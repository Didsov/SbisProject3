# Равномерная отправка и контроль ответов MX

Боевые пути `src.mailing.sender` и `src.mailing.etrn send` используют общий
`src.mailing.control.dispatch`. Очередь остаётся в `mail_recipients`, попытки —
в `mail_messages`, отчёты — в прежних `mail_runs` и `mail_events`.
Шаблоны, отправитель, DNS, маршрутизация Postfix и tracking_token не изменены.

## Поведение

Письма передаются последовательно. Между завершением предыдущего обращения
к SMTP и началом следующего выдерживается как минимум глобальный интервал
и интервал соответствующего провайдера. Это консервативнее интервала между
началами передач: длительный SMTP-запрос увеличивает расстояние между письмами.
Разрешения не накапливаются. Последние времена сохраняются в SQLite.

ЭТрН больше не использует случайные задержки 6–8 секунд и cooldown 40–50 минут.
`ETRN_BATCH_LIMIT`/`ETRN_BATCH_SIZE` остаются для preview; реальные отправки
проходят доступную очередь. Нумерация запусков и отчётность сохранены.
Старое поле `next_send_at` сохранено для совместимости, но отправку не блокирует.
При ожидании MX или временных проблемах DNS worker проверяет очередь каждые
5 секунд, обслуживая другие доступные направления. При постоянной паузе,
неисправном сборщике, суточном лимите или неизвестном исходе SMTP worker
заканчивает текущий проход; неотправленные записи остаются в очереди.

Начальные настройки (хранятся в SQLite, общие для всех процессов):

| Ключ | Значение |
| --- | ---: |
| `global_interval` | 23 секунды |
| `provider_interval` | 23 секунды |
| `consecutive` | 3 |
| `window_size` | 20 |
| `window_spam` | 5 |
| `max_unanswered` | 5 |
| `heartbeat_timeout` | 60 секунд |
| `daily_limit` | 1000 |

Это эксплуатационные настройки, а не гарантированные лимиты сервисов.
Существующий `daily_run --limit` сохранён (по умолчанию 1000). Ранее отдельного
суточного счётчика в проекте не было. Новый общий `daily_limit` считает попытки
передачи за календарные сутки UTC, включая неопределённые и неуспешные попытки;
для старых писем учитывается `sent_at`. Повторный запуск не обнуляет счётчик.

Провайдер определяется DNS MX через `dnspython`, с кешем до часа (не дольше TTL),
ошибка кешируется на 60 секунд. Mail.ru, Gmail и Яндекс группируются также для
корпоративных доменов. Сравнение — точное имя MX или граница DNS-суффикса.
Неизвестные MX группируются по отсортированному набору имён. Неоднозначные
смешанные MX и ошибки DNS откладывают письмо.
Настраиваемое сопоставление в env-файле (JSON, заменяет стандартное):

```dotenv
MAIL_MX_PROVIDERS='{"mailru":["mail.ru"],"gmail":["google.com","googlemail.com"],"yandex":["yandex.net","yandex.ru"]}'
```

После изменения сопоставления дождитесь истечения кеша (до часа).

## Остановка и возобновление

`paused_spam` фиксируется при трёх итоговых антиспам-отказах подряд либо пяти
среди последних двадцати итоговых ответов; полного окна ждать не нужно.
`delivered` и другой окончательный отказ прерывают серию, но не очищают окно.
`deferred` не входит в окно и блокирует новые передачи провайдеру до получения
итогов по всем его отложенным письмам. Python не повторяет доставку, которую
уже выполняет Postfix. Существующие повторы ЭТрН сохранены только для явной
неуспешной передачи в локальный SMTP.

Управление через CLI, без запуска рассылки:

```console
python -m src.mailing.control status
python -m src.mailing.control pause
python -m src.mailing.control resume
python -m src.mailing.control pause --provider mailru
python -m src.mailing.control resume --provider mailru
python -m src.mailing.control configure --set global_interval=23 --set provider_interval=23
python -m src.mailing.control configure --set consecutive=3 --set window_size=20 --set window_spam=5
python -m src.mailing.control configure --set max_unanswered=5 --set heartbeat_timeout=60 --set daily_limit=1000
```

Общее `resume` снимает только общую ручную паузу. Для `paused_spam` необходимо
явное `resume --provider ...`. Оно создаёт новый период с пустыми счётчиками,
сохраняя предыдущий период и диагностический ответ. Старые письма остаются
привязаны к старому периоду, включая их запоздалые ответы. Отказанные письма
не ставятся обратно в очередь. Таймера автоматического снятия `paused_spam` нет.
Возобновление периода не снимает ожидание уже имеющихся `deferred` доставок.

В `status` видны причина, время, счётчики и диагностический ответ остановки,
количество непереданных писем и переданных без итога по каждому уже определённому
провайдеру. `unresolved_provider` показывает ещё не классифицированную очередь.
`deferred_deliveries` объясняет блокировку активного провайдера. Общие поля
`paused`, `active_message`, `heartbeat_age` показывают дополнительные блокировки.
Остановка сразу записывается в Python logging/journal, а сводка включена в
существующий дневной email-отчёт на `DAILY_REPORT_EMAILS`.

## Сборщик Postfix

```console
python -m pip install -r requirements.txt
python -m src.mailing.postfix_delivery --log /var/log/mail.log --watch
```

Добавлен пример `deploy/projectsbis-postfix-delivery.service`. Его установка
и запуск выполняются оператором на сервере. Процессу нужен доступ к mail.log,
mail.log.1 и той же SQLite, что использует worker. Этот документ не запускает
и не включает службы; боевую отправку после обновления запускать отдельно.

Однократный запуск сборщика сохранён. `--watch` повторяет импорт каждые 5 секунд.
Heartbeat выставляется после успешной полной обработки снимка журнала, даже
если новых строк нет; при изменении файла во время импорта проверка повторяется
на следующем проходе. Отсутствующий журнал, ошибка БД/разбора или неполный проход
с `--limit` не подтверждают здоровье сборщика. Просроченный heartbeat запрещает
новые передачи. Отсутствие bounce не означает delivered.

Сборщик читает текущий журнал и несжатый `mail.log.1`, сохраняет соответствия
Message-ID/queue ID между проходами, поддерживает ISO-время и классический syslog
(локальная зона сервера, год определяется относительно mtime файла).
После простоя дольше доступной ротации старые архивы нужно импортировать отдельно
после распаковки; неизвестные результаты не становятся успешными автоматически.
Полное повторное чтение сохранено из прежней реализации; на больших журналах
следует контролировать время прохода и heartbeat.

## Данные и сбои

Миграция вызывается из `initialize_mailing_tables`, добавляет таблицы
`mail_control`, `mail_providers`, `mail_provider_periods`, `mail_mx_cache`,
`mail_delivery_events`, `mail_queue_ids` и nullable-поля в существующие сообщения
и получателей. Старые строки и статусы сохраняются. Результат дополнен
`result_reason`: `spam_rejected`, `invalid_recipient`, `temporary_failure`,
`other_failure`; успешный результат имеет NULL. Код 550 сам по себе не определяет
ни спам, ни несуществующий адрес.

Все MX-события содержат полный исходный ответ, DSN, relay, время, получателя,
Message-ID через связь с сообщением и queue ID. Хеш исходной строки устраняет
дубли импорта. В счётчиках учитывается только первый итог одного сообщения,
в порядке времени события и стабильного хеша при совпадении времени.

Используется существующая межпроцессная OS-блокировка проекта, отдельный файл
рядом с SQLite (`*.mail-send.lock`), и короткие транзакции SQLite. Это рассчитано
на процессы одного сервера с одной локальной БД. Блокировка удерживается до
завершения SMTP и сохранения результата; Message-ID сохраняется до SMTP.
При аварии/неоднозначном разрыве соединения `active_message` блокирует новые
передачи. Оператор сверяет эту запись с Postfix по Message-ID. После сверки:

```console
python -m src.mailing.control acknowledge-handoff
```

Команда снимает общую блокировку неопределённой передачи, но не пересылает и
не меняет статус самого письма. Незавершённая попытка остаётся занятой; её
восстановление требует отдельной сверки. Это предотвращает автоматический дубль
при сбое между принятием SMTP и фиксацией в SQLite.

Остановка Python не отзывает письма, принятые Postfix. Их результаты могут
появиться позже. Команд очистки, удаления или удержания очереди Postfix нет.

## Проверки

```console
python -m pytest -q
```

`tests/test_mailing_control.py` использует временную SQLite, поддельный SMTP,
управляемые часы и искусственные журналы. Проверяет интервалы, простой/перезапуск,
конкурентные задачи и отдельный процесс, пороги остановки, независимость
провайдеров, порядок MX-событий, повторный импорт, ротацию, heartbeat, лимиты,
ручные периоды, неопределённую передачу и миграцию старой схемы.
Тесты ЭТрН обновлены: вместо cooldown проверяется равномерное прохождение очереди;
сохранены проверки подмены тестовых адресатов, вложений и локальных SMTP-повторов.

Локальный результат проверки: **120 passed, 34 subtests passed**; `git diff --check`
без ошибок. CLI `control --help` и `postfix_delivery --help` проверены.
Зависимость dnspython установлена в локальную `.venv`; DNS-адаптер проверен
поддельным ответом, без сетевого запроса. Рабочая SQLite не мигрировалась,
реальная рассылка и серверные службы не запускались. Linux/systemd требует
отдельной проверки при установке на сервере.
